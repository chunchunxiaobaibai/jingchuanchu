## 优化顺序与完成条件

1. **先保证检查命中工作区。** 统一 Windows 或 WSL 的 Node 与依赖安装，恢复锁文件声明的 workspace 链接；检查真实路径确实落在 packages，再运行对应源码测试。独立 tgz 消费验证继续保持独立，以分别覆盖开发源码和交付包。本轮遇到 Linux tsx 无法使用 Windows esbuild，改用现有 Windows Node 执行。
2. **继续按具体缺陷完善生命周期。** 本轮已修复取消等待与销毁错误丢失。后续仅在发现实际故障时增加直接回归；优先关注加载取消、场景切换和模块回滚的边界，不为假设性组合扩大全量测试。
3. **性能先选真实瓶颈。** 现有测量显示 ECS 查询与绘制遍历已有收益，默认系统诊断开销没有显著提速。下一轮以实际游戏规模选择查询分配、系统计时或碰撞候选为单一目标，记录同环境前后中位数、离群值与行为契约。没有测量前不引入 Archetype、TypedArray 或跨帧层级缓存；可直接修改的 layer/transform 需要明确失效契约。
4. **应用套件按最小闭环推进。** 先依现有规范界定应用挂载、实例上下文和卸载的首个范围，再接入一个场景和一个三文件 UI 组件；以独立项目能够创建、静态构建及释放实例为完成条件。组件/场景生成命令跟随真实接口实现，避免生成尚不存在的 API。核心用户仍可按需组合原有 8 个包。
5. **2D 扩展由游戏需求驱动。** 优先让现有相机、动画、碰撞与输入在模板中形成小型可选示例，再按明确需求决定音频、瓦片地图等能力。浏览器画面、交互和帧耗时须由用户明确授权后验证，Node 模拟结果不能代替真实渲染指标。
