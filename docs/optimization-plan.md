# 引擎优化讨论方案

状态：待讨论，未实施。目标是同时补强稳定性与开发体验、运行性能、2D 制作能力；仍限于 TS、网页和 2D，网络按需引用，目标游戏规模暂为每局最多 10 人。

下面的代码观察来自当前 0.3.0。它们是需要测量或验证的候选问题，不能据此声称已出现性能瓶颈或承诺提升倍数。

## 第一阶段：内核契约与开发体验

| 方向         | 当前情况                                                   | 建议                                                                                                             |
| ------------ | ---------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| 系统调度     | fixed/render + order；addSystem 时排序，执行时复制系统数组 | 明确执行中增删系统的生效时机，补 before/after 依赖排序；同序保持稳定，启动前拒绝冲突                             |
| ECS 结构变更 | 查询采用 handle 快照；支持 defer，flush 时取出一批命令     | 写清新增、删除、销毁和嵌套 defer 的可见性，覆盖失败与中断路径，再考虑批量命令接口                                |
| 错误与诊断   | 有系统耗时记录、生命周期错误和反向清理                     | 统一错误上下文、按需开启诊断、提供模块与系统状态查询，避免游戏自己读内部字段                                     |
| 生命周期     | 同步 setup、全引擎 dispose；没有异步 setup 或单模块卸载    | 先完善取消和资源归属，再引入场景生命周期；异步准备采用独立 prepare/start 流程，避免直接改变现有同步 install 语义 |
| 资源         | AssetCache 共享 Promise、失败重试、整体清空                | 增加按项释放、加载状态、取消策略与引用持有机制；错误通过调用方可观察，不让晚到的资源泄漏                         |
| 网络         | 连接、decoder、限流和心跳已有；解码与业务回调共用异常处理  | 将无效消息与业务处理失败分开报告；重连作为可选策略，明确队列上限与停止取消，不默认恢复玩家身份                   |

先明确契约，再添加小范围 API。所有公开变更需配消费例子、回归验证和版本说明。模块动态卸载需要依赖级联与资源归属，暂不与场景切换一起实现。

## 第二阶段：测量后优化热路径

先建立无渲染 ECS、固定循环与浏览器 Canvas 三类基线。建议场景：100/1,000/10,000 实体，1/2/4 组件交集；创建销毁、重复查询与层级改变分别测量。10,000 实体是压力样本，不是首版功能要求。

记录查询与系统耗时、帧耗时分位数、内存与 GC 波动；网络记录每秒消息数、字节数、积压和恢复耗时。浏览器在同一设备、同一配置下比较，避免把 Node 查询成绩当作网页性能。

| 候选优化           | 代码依据                                               | 必须守住的语义                                                                    |
| ------------------ | ------------------------------------------------------ | --------------------------------------------------------------------------------- |
| 查询计划与复用缓冲 | World.query 每次解析 stores、复制候选并创建冻结 handle | 保持 World 所属、代际校验和遍历期间回收复用安全；新接口可以采用明确的只读迭代契约 |
| 固定/渲染系统列表  | Engine.run 每阶段复制全系统列表并过滤；每系统默认测时  | 调度只在结构变化时重建，关闭诊断时减少测时；不能改变系统内 dispose 的中断行为     |
| 绘制排序与数据访问 | Canvas2D.drawWorld 每帧查询、排序，比较时重复 require  | 可先取位置/形状绘制项；缓存排序需要处理 layer 直接修改，不能只监听 set/remove     |
| 网络发送           | send 每次 JSON 序列化；只提供 bufferedAmount 上限      | 仅对高频可丢弃消息做可选合并；可靠命令不静默丢弃，协议内容继续由游戏定义          |
| 资源缓存边界       | 缓存没有容量或单项移除接口                             | 先观察真实资源规模，再增加容量/引用策略；正在使用的资源不能提前释放               |

不直接把 Map 全换成 TypedArray，不先重写 Archetype ECS，也不预设 WebGL/WebGPU。只有基线表明瓶颈且改善可复现时，才扩大改动。

## 第三阶段：补齐网页 2D 制作能力

1. **变换与相机**：补位置、缩放、旋转、父子关系、世界/屏幕坐标；明确循环父子引用拒绝、更新顺序和像素比/resize 行为。
2. **精灵与动画**：图片资源、图集帧、锚点、翻转、透明度和层级；动画帧按 fixed 时间推进，绘制位于 render，暂停/重启语义与 Engine 一致。
3. **场景管理**：进入、暂停、恢复、退出，场景拥有实体与 Scope；切换清理旧输入/订阅/资源。底层 Engine 可复用，共享网络是否跨场景由应用显式选择。
4. **基础碰撞**：仅 AABB/圆形检测与碰撞事件，先服务简单玩法。完整刚体、约束与复杂物理后置。
5. **网络制作能力**：可选心跳状态、重试退避、队列策略和连接错误分类；快照/增量协议、身份和重连恢复仍在游戏层。

变换、精灵和动画先放 renderer-2d 的公开子入口，避免新拆大量 npm 包；场景能力如果只依赖 core/ecs，可独立为 scenes 包，最终边界在 API 讨论时确定。新增功能不应让只用 core 的项目安装 DOM 或网络依赖。

## 建议迭代顺序与验收

| 阶段 | 交付                                        | 验收                                                                 |
| ---- | ------------------------------------------- | -------------------------------------------------------------------- |
| A    | 调度/变更契约、诊断开关、资源与网络错误边界 | 生命周期、错误恢复与外部 TS 消费验证通过，未引入隐式行为变化         |
| B    | 性能基线、按测量选中的查询/循环/排序优化    | 同机基线可复现，结果和风险公开；已有实体安全、清理与执行顺序测试通过 |
| C1   | Transform、Camera、Sprite、Animation        | 浏览器运行精灵移动/动画，验证暂停、resize、层级与坐标转换            |
| C2   | Scene 与基础碰撞                            | 多次场景切换后实体/监听/资源数量回到预期，单机组合不引入网络         |
| C3   | 可选网络策略与 10 人样本                    | 断线、慢连接、积压和退出可验证；游戏明确决定身份和状态恢复           |

每阶段都保持 npm 按需消费、文档和 starter 可运行。先讨论 API 与验收，再实现；不为了目录归档把这些实现混入当前变更。

## 需要在实现前定下的选择

建议继续使用现有稀疏集 ECS；短期渲染仍为 Canvas 2D；诊断默认关闭或按开发配置开启；自动重连需显式启用；场景负责游戏资源，公共服务由应用明确持有。

三个方向都会做，仍按 A → B → C1 → C2 → C3 分阶段。第一轮重点是能稳定制作简单网页游戏；编辑器、3D、桌面适配和大规模联机继续排除在当前范围之外。
