# 2026-11-02 性能审查与测量

## 范围与结论

审查当前网页 2D 引擎的 ECS、固定步调度、Canvas 绘制、碰撞及参考游戏的应用接入路径。当前工作区已有文档、脚本迁移等改动，本轮保留这些改动；优化前 renderer 使用 HEAD `5776288f112f19eb07ae9a9693d073a8e52e4be6` 中的原文件，其内容与本轮开始时的 renderer 相同。其他运行模块使用当前工作区源码。

相同简单工作量下，当前 ECS 更新与绘制提交确实比直接操作 JS 数组更慢。功能测试通过不能证明性能达标。引擎提供实体有效性、查询快照、组件组合、图层等能力，但现有实现也存在可以削减的热路径开销。不能把微基准倍数直接写成完整游戏 FPS 差距。

## Node 对照方法

- Windows x64，Node v24.12.0，Intel Core i7-12700H。
- 原生 JS 和引擎在同一个进程内交替测量；相同数量的数据、相同位移、相同矩形和图层，每帧都进行稳定图层排序。原生路径也写 fillStyle 和调用 fillRect。
- 每个场景先预热 8 次，然后采样 21 批，每批 30 次；报告每次迭代的中位耗时。JSON 的 p95 是批平均值的分位数，不是逐帧尾延迟。
- 移动结果进行逐对象相等校验；绘制使用顺序敏感校验和与调用数校验，防止比较不同工作量或无效空循环。
- 此处 Canvas 是记录调用的模拟对象，只测 JS 更新、遍历、排序和提交路径，不测实际像素渲染、GPU、布局、输入延迟或真实游戏 FPS。
- 全量源码测试结束后，顺序重测优化前、优化后，再独立重复一次优化后原生对照。最初与全量测试同时执行的数据已被这些结果覆盖。

| ------ | -------- | -------- | -------- | ------------ | ------------ | --------- |
| 100    | 0.00100  | 0.01226  | 12.3×    | 0.00613      | 0.02944      | 4.81×     |
| 1,000  | 0.00541  | 0.08478  | 15.7×    | 0.07422      | 0.21528      | 2.90×     |

## 已实施的优化

`packages/renderer-2d/index.ts` 的 drawWorld 原先先创建 shapes/sprites 数组，再 map 为带 layer 的对象，其中对象展开又复制每个绘制条目，最后合并排序。现在直接构建最终绘制队列，每个条目只创建一次。仍按原先三个遍历阶段插入，保留同层顺序；仍读取当前组件，不缓存可变组件的 layer 或位置。

| 对象数 | 优化前绘制 ms | 优化后 ms | 优化后复测 ms | 两次降幅  |
| ------ | ------------- | --------- | ------------- | --------- |
| 100    | 0.03097       | 0.02944   | 0.02999       | 3.2%–4.9% |
| 1,000  | 0.23708       | 0.21528   | 0.21415       | 9.2%–9.7% |
| 10,000 | 3.04717       | 2.76006   | 2.94765       | 3.3%–9.4% |

这是小幅改善，不能宣称整体游戏获得同等幅度提升。原有 core 基准中 100 个对象的短批次还有反向波动，不能宣称所有规模都稳定提速。没有改变公开函数名或默认开关，也没有重写内核。

新增回归覆盖：Position/Transform/Shape/Sprite 混排的同层顺序、同时拥有 Position 与 Transform 的形状不会重复绘制、直接改变 layer 后下一次绘制立即生效、销毁实体后不再绘制。

## 后续优化优先级

1. **优先处理 ECS 批量访问。** `World.query` 每次复制候选索引，再复制句柄快照，每个实体执行 isAlive 与 stores.every。调用方接着 require，又进行存活检查和 Map 查找。移动基准直接测得这整条路径显著慢于数组更新，尚未通过 CPU profile 将比例进一步分解到各函数。建议为性能敏感系统新增显式批量组件遍历入口，保留当前 query 的快照、索引回收和遍历期间增删语义；不要直接删除存活检查或悄悄改为遍历底层可变数组。
2. **继续降低渲染队列和排序成本。** 本轮只删除中间复制。drawWorld 仍每帧进行三个查询、构建条目、稳定排序和组件访问。若新增缓存，必须处理直接修改 layer/Transform/Position、组件移除、销毁与索引复用，现有 API 允许直接修改组件对象，不能依靠 world.set 才失效的缓存。纹理精灵、层级变换与相机的瓶颈需要另测，本轮矩形基准不能代替这些场景。
3. **明确生产诊断开关。** Engine 默认开启逐系统计时，每次 update 前后调用 performance.now 并创建 timing 记录。原有基准中 1,000 个空系统、每批 100 次 advance，开启/关闭分别为 10.54/1.21 ms，约 8.7×；绝对值约为每次 advance 多 0.093 ms。这是大量空系统的边界场景，不能据此认定参考游戏的少量系统被拖慢 8.7×。生产项目可以显式设置 `new Engine({ diagnostics: false })`，GameCanvas 可通过 `options.clock.diagnostics` 设置。
4. **按真实 profile 再处理输入与碰撞。** ActionSampler.read 每个固定步创建快照并 structuredClone/递归冻结；碰撞每次重建世界包围体并排序，X 轴候选密集时内层扫描可退化为平方级。这些是静态审查发现的成本与边界风险，尚未单独量化，不能列为已确认的游戏掉帧根因。参考游戏每步更新剩余时间会触发响应式传播，但 HUD 已使用 computed 对秒数取整，不能直接声称它每步重建 DOM。

## 获得授权后的真实浏览器验证

用户明确授权后执行。Chrome 156.0.8078.74，Windows、本机 headless、1280×900、DPR=1、不做 CPU 降速，使用 Vite 生产构建。系统枚举包含 RTX 3060 Ti 与 Microsoft Basic Render Driver；设备枚举不等于已确认每个 Canvas 的实际 GPU 执行路径。浏览器计时单位均为 ms。

**先发现并修复了一个独立的启动缺陷。** 参考游戏首页→选关→开始旅程后，游戏画布没有创建成功。错误链为 `Component game-canvas: onMount failed` → `GameCanvas create failed` → `Viewport requires a canvas container and document window, or an injected driver`。条件分支来自 template.content，真实浏览器中它属于没有 defaultView 的惰性文档；createView 在插入分支前挂载子组件，Canvas 因而拿不到文档窗口。

修复位于 `packages/app/runtime/component-runtime.ts`：构造条件/列表/插槽分支时，先用宿主文档 adoptNode 接管 fragment，再绑定与挂载子组件；保留原先分支插入和生命周期顺序。原有 happy-dom 模拟没有忠实复现 template 内容文档的行为，因此这个缺陷以真实浏览器中的参考游戏启动、活动帧、暂停/恢复和无页面异常检查作为直接回归。初始错误证据保存在 [browser-game-failure.json](browser-game-failure.json)，这是修复前记录，不表示最终状态仍失败。

原生/引擎矩形对照分别创建独立 Canvas，均真实执行 Canvas API；每组预热 30 帧、采样 120 帧，两轮反转原生/引擎的顺序。相同一组的最终像素哈希一致。第一次复用 Canvas 的试运行出现跨轮哈希不同，已弃用；最终数据采用独立 Canvas。下表范围来自两轮中位数：

| 对象数 | 原生更新 | ECS 更新 | 原生绘制提交 | 引擎绘制提交 | 两边帧间隔中位数 |
| ------ | -------- | -------- | ------------ | ------------ | ---------------- |
| 1,000  | 0.0–0.1  | 0.2      | 0.3          | 0.6          | 16.7             |
| 10,000 | 0.3–0.4  | 1.6–1.8  | 2.4–2.5      | 3.4–3.5      | 16.7             |

两边全部 960 个采样帧间隔中，超过 25 ms 的数量均为 0。原生 1,000 个对象的更新中位数出现 0，是浏览器计时精度所致，不能拿它作除数。drawSubmission 是 Canvas 调用和 JS 提交耗时，不是 GPU 完成时间；rAF 间隔也不是屏幕呈现延迟。测量说明引擎消耗更多 CPU 预算，但本机本场景尚未因此降低显示刷新节奏。

参考游戏在修复后另开会话、待其他测试结束再采样：第一关 1 个玩家、8 个收集物，连续驱动左右键约 6 秒。记录 362 个游戏帧回调，倒计时从 30 秒变为 24 秒；rAF 回调 CPU 中位数 0.4、p95 0.7、最大 1.5；帧间隔中位数 16.7、p95 16.9、最大 16.9，无超过 25 ms 的间隔。整个采样期间 CDP ScriptDuration 增量约 243.88 ms，LayoutDuration 约 2.38 ms；这些总量与 rAF 回调统计有交叠，不相加。暂停后停止请求帧、恢复后重新请求帧，页面未捕获异常为 0。此处没有制作同玩法的原生 JS 游戏副本，不能据此比较完整参考游戏与原生版本的 FPS。

原始数据：[browser-comparison.json](browser-comparison.json)、[browser.json](browser.json)。对照场景与参考游戏分开会话测量；最终 browser.json 的 comparisons 复用了已保存的同版本对照结果。参考游戏的 6 秒采样不能证明长时间无泄漏，也没有覆盖触屏、音频解锁、后台恢复、其他关卡完整通关或目标移动设备。H01—H04 不因此整体标记完成。
