## 新发现与修复验收条件

### A01 / P1（源码已修复）：computed 的上游强引用在使用方销毁后仍存在

位置：`packages/app/runtime/reactivity.ts` 的 computed 依赖登记与 effect 清理。

修复前，每次 computed 求值都将其节点加入上游 `dependents`，节点上的 `refresh` 又持有 `read` 和业务 `derive`。effect 的 Scope 销毁仅删除 effect 自身，上游仍强持有不再被观察的 computed。因此，应用级 Store 中长寿命的 signal 可以持续保留已退出页面的派生闭包及其捕获对象。

独立 Node 复现：保留一个共享 signal，为 20 个临时 Scope 各建立一个捕获 marker 的 computed/effect，等待首次执行后全部 dispose，跨事件循环进行 8 轮显式 GC。WeakRef 结果为 `computedRetained:20`；同样流程但 effect 直接读取 signal 的对照组为 `directRetained:0`。这是对象保留证据，不是浏览器内存曲线、帧耗时或设备性能结论。

修复验收：不再使用的派生节点及捕获的页面数据可回收；直接读取的 computed、动态依赖、异常后恢复、缓存与重新订阅仍正确。以有对照的 Node 回收验证和必要的定向行为测试确认，随后在 H03 的反复进出页面中复核实际浏览器表现。

实际修复：反向订阅采用弱引用，使用方对依赖仍保持强引用，活动 effect 仍由 Scope 持有。显式删除时注销回收登记，失去使用方的节点回收后清除订阅元数据，不增加 computed 公共 API。原复现的 `computedRetained` 已从 20 降为 0；新增隔离 GC 回归同时验证无观察者的 computed 可回收、活动 effect 的依赖跨 GC 后仍能响应写入。

### A02 / P2（源码已修复）：动态选项的 select 初始值与 model 不一致

位置：`packages/app/runtime/template.ts` 的提交顺序及 `models.ts` 的 select 写入判定。

模板如下，初始 `value = signal('b')`、`items = signal([{id:'a'},{id:'b'}])`：

```html
<select model:value="value">
  <template each="item of items" key="item.id">
    <option :value="item.id">{{ item.id }}</option>
  </template>
</select>
```

修复前编译检查成功，在 Node DOM 挂载并等待 nextTick 后，实际输出为 `model:"b", dom:"a", options:["a","b"]`。原因是先应用 model，后插入选项；后续 model 值未变化，绑定缓存跳过重写。默认参考游戏目前没有使用 select，这项影响公开表单/模板能力。

修复验收：首次渲染、异步增加选项和选项替换后，单选/多选控件与 model 一致，结构更新不会凭空触发业务输入；现有数字草稿、IME 和光标行为保持正确。当前复现为 Node DOM 证据，真实浏览器表现仍需 H02 验证。

实际修复：select 的 model 在属性、条件分支和列表选项更新完成后应用；即使 model 未变，也检查选项变化造成的选择差异。目标选项不存在时，空选择不误判为需要重复写入。新增回归覆盖单选/多选首次挂载、异步选项、移除/恢复选中项及真实 input 回写；结构更新不触发 input/change 事件。原复现现在为 `model:"b", dom:"b"`。
